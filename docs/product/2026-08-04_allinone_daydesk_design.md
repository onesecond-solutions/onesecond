## 0. 한 문장 원칙

> **"날짜(또는 고객)를 누르고, 한 칸에 그냥 적으면, 시스템이 알아서 6종으로 분류해 하나의 타임라인에 쌓는다 — 종류·제목·필수필드·화면이동 0."**

## 0.5 제품 전략 — 팀 공용 & 개인 전용 이원화 (2026-08-04 대표 확정 · 최상위 방향)

> **최종 목표(대표): 데이데스크를 두 방향으로 이원화한다.** ① **팀 공용** — 공지사항 중심의 데이폴더를 **팀에 먼저** 배포해 쓰게 하고 → ② 사용자가 마음에 들면 **개인 전용**으로 자기 상담·고객·메모까지 확장해 쓴다.

이 이원화는 §4의 **A/B 격리 2클래스와 정확히 1:1로 맞아떨어진다** — 즉 별도 설계가 아니라 **같은 데이데스크 껍데기를 "모드"로 나누는 것**이다.

| | **팀 공용 데이데스크 (1단계 · 먼저 배포)** | **개인 전용 데이데스크 (2단계 · 확장)** |
|---|---|---|
| 담는 것 | 공지사항 · 팀 자료실 · 팀 노트 | 상담 · 고객 · 개인메모 · 개인노트 · 개인일정 |
| 격리 클래스 | **B계열** (audience_target / branch) | **A계열** (owner_id / author_id RLS) |
| 누가 보나 | 팀원 전체 같은 타임라인 | **본인만** (팀장·지점장도 타인 것 못 봄) |
| PII | 없음 → **신뢰·도입 장벽 낮음** | 있음 → owner RLS 격리 필수 |
| 목적 | "팀에 공지 심플하게 보여주는 데이폴더" | 상담·고객관리의 복잡성 해소(개인 CRM) |
| 실사례 | theone_cityhall(더원 시청팀 팀홈)이 사실상 이 1단계 | 현행 상담관리/고객관리를 흡수 |

**전환 UX:** 화면 상단에 **[팀 공용] ↔ [개인 전용] 모드 토글** 하나. 토글이 바꾸는 것 = ① 타임라인이 조회하는 격리 클래스(B or A) ② 통합 입력의 저장 라우팅 대상 ③ 팀공유 토글 노출 여부.

**도입 시퀀스(대표 전략):** 팀 공용을 먼저 깔아 "쉽다"는 경험을 팀에 심는다(진입 장벽 최소) → 개인 전용은 그 신뢰 위에 각자 켜서 자기 고객·상담을 심플하게 관리. **개인 전용을 강요하지 않고, 마음에 들면 켜는 opt-in 구조.**

⚠️ **격리 불변식(이원화의 안전 축):** 팀 공용 모드에서는 **A계열(상담·고객 PII)이 절대 조회·표시되지 않는다.** 개인 전용 모드의 A계열은 **owner 본인에게만.** 두 모드는 데이터를 섞지 않는다 — 껍데기만 공유, 원장·RLS는 완전 분리(§4).

**신규 고객 + 첫 상담:** `+고객 추가`(`_ciNew :2340`) → 필수 3필드(이름\*·생년월일\*·휴대폰\*, `:17475·17477·17482`) → 저장 → **카드 재클릭(consult 모드 재오픈)** → 상담입력 → 저장. **클릭 ~7회 + 저장 2회 분리 + 필수 3필드 강제.**

### 1-B. 상담관리(청약 전) ↔ 고객관리(청약 후) 분리
- **날짜가 아니라 status 기준**(2026-07-13 대표 확정 · PR2 2026-07-30):
  - 상담관리(care) = `status !== '신규'` 전량
  - 고객관리(salesnote) = `status === '청약완료'`만 (`_ciViewData :16327~16344`)
- **둘은 물리적으로 같은 컴포넌트.** `#ci-wrap`(4분할)을 `_ciShow()`(상담관리)와 `_snCiShow()`(고객관리)가 **호스트만 바꿔 재사용**(`:16368~16370`). 차이는 `window._ciMode`('care'|'salesnote') 분기뿐.

### 1-C. 원장(테이블)
- 상담·고객 공통 정본 = **`sales_customers`**(owner RLS). 상담이력=`profile.consult_log[]`, 첨부=`profile.attachments[]`, 속성=`profile.*` (JSONB).
- **레거시 이중 저장 부채**: 옛 회차 테이블 **`sales_consultations`**(customer_id·owner_id·memo, `:4243, :4270`)도 존재. 표뷰는 consult_log 우선, 없으면 `sales_consultations.memo` 폴백(`:17895`) → **정본이 두 곳**.

### 1-D. 복잡함의 근본 원인 5
1. **"고객 레코드 우선" 모델** — 그냥 적을 수 없고, 모든 상담은 먼저 존재해야 하는 고객의 자식(`:17533~17540`). "날짜→타이핑→끝"의 정반대.
2. **초대형 단일 폼** — `_ciFormHtml`이 6섹션·약18필드·필수 3개를 한 번에 렌더(`:17467~17516`). 한 줄 적으려 해도 폼 전체를 지남.
3. **모드 곡예(consult↔edit)** — 기존 고객은 잠금으로 열리고, 수정하려면 '정보수정'으로 잠금해제. 상담입력은 '상담입력↔저장하기' 토글(폼 안 또 2단계, `_ciFormSetMode :17583`).
4. **status로 갈린 두 화면의 인지 부담** — 청약완료되면 상담관리→고객관리로 이관, 고객관리에선 상담입력 차단(`:16329, :17565`). 대상이 어느 화면에 사는지 매번 추론.
5. **다층 왕복** — 6종이 각기 다른 뷰(공지=posts, 자료실=vault, 메모=library FAB, 노트=scripts)에 흩어져 화면 이동 상시.

## 2. 통합 모델 — 6종을 하나로 녹이는 법

**핵심**: 6종은 이미 **두 개의 격리 클래스**로 깔끔히 나뉜다(§4). 통합 입력은 "무엇을 붙였는가"로 종류를 자동 판별하되, **저장은 격리 클래스별로 원래 규칙대로 분기.** 즉 **UX는 한 칸, 저장은 격리별로 분기.**

이미 코드에 선례가 있어 신기술 아님:
- 업무노트 뷰가 여러 종류를 `_type` 배지로 한 리스트에 병합(`:13851`).
- 좋아요/댓글이 `source_type`+`source_id` 폴리모픽 키로 여러 원장을 가로지름(`:4912, :4929`).
- 공개범위(scope) 셀렉트가 role별 personal/team/branch로 이미 표준화(`:15702~15704`).

## 4. 데이터·권한 아키텍처 — "UX는 통합, 데이터는 격리"

### 원장 매핑 & 격리 클래스 (모두 현존 테이블)
| 종류 | 원장 | 격리 | 근거 |
|---|---|---|---|
| 상담(청약 전) | `sales_customers.profile.consult_log` | **owner RLS (PII)** | `:16407, :17537` |
| 고객(청약 후) | `sales_customers` (status=청약완료) | **owner RLS (PII)** | `:16459, :16329` |
| 메모 | `library` | owner_id | `:5324` |
| 노트(개인) | `scripts` scope=personal | owner_id | `:6191` |
| 일정(개인) | calendar, audience=personal | author_id | `:15703` |
| 공지/자료실(팀) | `posts` / `scripts` team | audience_target/branch | `:5232, :3580` |

→ **두 클래스로 자연 분리**:
- **A. 개인격리(owner_id/author_id)** = 상담·고객·메모·개인노트·개인일정 → **PII 포함, 대원칙 그대로**(owner_id 격리·통합검색 제외·팀장/지점장 열람금지·공용DB 분리, `CLAUDE.md:40`).
- **B. 공용/팀(audience_target/branch)** = 공지·팀 자료실.

### 격리를 깨지 않고 한 타임라인에 공존시키는 4규칙
1. **저장(라우팅)**: 판별 결과가 A계열이면 **반드시 owner_id/author_id=본인**으로 INSERT. B계열(팀공유 ON)만 posts/scripts(team)로 audience 부여. **상담·고객(PII)은 팀공유 토글 자체를 비활성**(노출 금지).
2. **조회(병합)**: 타임라인은 **원장별로 각각 질의** 후 클라이언트에서 시간순 병합(`_type` 병합 `:13851` 확장). A계열은 owner RLS가 서버에서 자동 필터 → 팀장이 봐도 타인 A항목 없음.
3. **통합검색 제외 유지**: 전역 검색 인덱스엔 B계열만, A계열(상담·고객)은 제외(`CLAUDE.md:40`). 통합 타임라인은 검색이 아니라 "본인 소유 원장의 개인 뷰".
4. **공용DB 분리 유지**: A는 sales_customers/library/scripts(personal), B는 posts로 물리 분리된 채. 통합은 **읽기 시점의 뷰 병합**일 뿐 테이블 병합이 아님.

> **핵심 문장: 격리는 "저장 원장 + RLS"에서 지키고, 통합은 "읽기 뷰"에서만 한다.**

## 6. 프로토타입 사양 (정적 HTML 클릭 목업 — DB 미연동)

`?view=daydesk` 가정. 실제 저장 없이 클릭 흐름만 증명. 요소·상태·동작:
- **`#dd-mode` 모드 토글(상단): [팀 공용] ↔ [개인 전용].** 팀 공용 → 타임라인이 공지·팀자료·팀노트만, 입력 액션바에서 `@고객` 숨김·`팀공유` 기본 ON. 개인 전용 → 상담·고객·개인메모·노트·일정만(본인), `@고객` 노출·`팀공유` 숨김. **두 모드는 타임라인 데이터를 섞지 않음(이원화 시연).**
- `#dd-cal` 월 달력: 날짜 셀 클릭 → composer 열림 + textarea 자동 focus(제목칸 없음). 오늘 셀 강조.
- `#dd-fab`(＋빠른입력): 어디서나 → 오늘 날짜 composer.
- `#dd-composer`: `textarea`(placeholder "그냥 적으세요…") + 액션바 `@고객`·`🕒시간`·`📎파일`·`#태그`·`[팀공유]`·`[저장]`.
  - `@고객` → 더미 고객목록 + "+새 고객: ___". 선택 시 칩 + 배지 '상담'으로 프리뷰.
  - 본문에 "10시" 타이핑 or `🕒` → 배지 '일정' 실시간 변경.
  - `📎파일` → 파일명 칩 → 배지 '자료'.
  - 팀공유 체크 → 배지 '공지[팀]'. **단 @고객 칩 있으면 팀공유 disabled**(PII 격리 시연).
  - `[저장]` → 타임라인 최상단 unshift(메모리 배열, 새로고침 시 소멸=목업 명시).
- `#dd-timeline`: 종류 배지(색)+첫 줄(제목)+@고객/날짜. 필터 칩 클릭 → 클라이언트 필터.
- **격리 시연 배너**: "이 타임라인의 상담·고객 항목은 본인에게만 보입니다(owner RLS)" 고정.
- 시연 3종: (a) 날짜→타이핑→저장=메모 2클릭 (b) 타이핑→@새고객→저장=상담 3클릭 (c) 타이핑+시간토큰→일정 자동. 각 상단에 "현행 N클릭→목업 M클릭" 카운터.
