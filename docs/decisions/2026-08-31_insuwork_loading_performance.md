# 보험워크 로딩 개선

- 날짜: 2026-08-31
- 대표 지시: 로딩 속도 점검 결과를 수정하고 라이브 반영까지 완료.
- 범위: 보험워크 PC와 모바일의 공통 조회 엔진·모바일 렌더 완료 시점. 데이폴더 변경 없음.

## 확인한 문제

- 홈 날짜 변경 시 일정 외 자료·고객·상담 등 5개 요청을 반복하고 전체 데이터 준비 상태를 해제했다.
- 그 뒤 캘린더 진입 시 자료 본문 약 3.5MB와 고객별 케어 확인 122건을 다시 조회했다.
- 점검 계정 기준 캘린더 첫 전환 REST 127건, 모바일 홈 REST 130건을 관측했다.
- 모바일 화면은 데이터 완료 신호 대신 누적 지연 타이머로 재확인했다.
- 홈 배경 이미지의 잘못된 상대 경로로 404 요청이 있었다.

## 유지할 기준

1. 홈 날짜 이동은 해당 날짜 일정만 조회한다. 다른 날짜 일정 및 자료·고객·상담 캐시는 보존한다.
2. 날짜 변경 응답은 요청 순번과 계정을 확인하고 최신 요청만 적용한다. 오류를 빈 일정으로 표시하지 않는다.
3. 기본 업무 데이터 준비와 전체 자료 준비 상태를 구분한다. 캘린더·모바일 홈은 전체 자료 본문을 기다리지 않는다.
4. 자료·검색 및 첨부 자료가 필요한 고객/상담 화면에서는 기존 전체 자료 조회를 유지하여 검색과 편집 동작을 보존한다. 자료별 본문 지연 조회로 전면 전환한 것은 아니다.
5. 케어 일정 확인은 1,000행씩 안정된 ID 순서로 페이지 조회한 후 고객별로 분류한다. 해당 계정·연도의 성공한 자동 동기화는 페이지 수명 중 반복하지 않는다.
6. 고객 생성·수정 때의 개별 케어 동기화와 기존 생성/수정 조건은 유지한다. 실패한 자동 동기화는 완료 처리하지 않는다.
7. 모바일 6개 화면은 `insuwork:data-ready` 이벤트로 데이터 조회·케어 갱신 직후 렌더한다.
8. DB DDL·RLS·인증 비밀은 변경하지 않는다. 테스트는 가짜 응답으로 수행하며 운영 데이터 직접 쓰기는 하지 않는다.

## 검증

- `node scripts/insuwork_loading.test.cjs`: 날짜별 단독 조회/기존 캐시 유지, 응답 역전, 본문 지연 로드, 실패 상태, 케어 페이지 조회/중복 방지, 기존 생성·수정 조건 검증.
- PC 로컬 실제 홈 렌더 확인. 병합 후 라이브 요청 수·전송량과 모바일 표시를 추가 확인한다.
